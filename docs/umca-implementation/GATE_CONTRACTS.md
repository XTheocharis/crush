## Owner subunits, audit and merge mechanics

1. ORCH adds S/H/O owner subunits to the actual DAG before scheduling the consuming operation. Explicitly separate schema/API contract from later consumer-specific wiring to avoid cycles; version the minimal contract and its fixtures. U05 can develop after G1 but merge waits for G2; the candidate must be refreshed/re-reviewed against accepted G2 if needed.
2. No new unit is based on trial merge HEAD. Accepted integration ref is never checked out; use attempt-specific trial worktrees and CAS promotion per orchestrator. One integration lease spans merge, candidate/dependency reconciliation, QA and integrated AUD, promotion or rejection and validation. ORCH writes a durable prepared promotion record, then CAS-updates the accepted ref, then reconciles the ledger and manifest; restart verifies actual SHA and pending stage before new work. A separate reviewer approves actual candidate and integrated SHA; no self-approval, even without agent spawn. Read-only investigation may use no-op merge but independent evidence remains required.
3. For each fixture list implemented boundary, exact test name/command, setup, observed expected predicate and logs. If split across stages, create suffix `.local`/`.remote` or `.core`/`.full`; later assertions stay pending in the release ledger. Test all states and supported targets. No mock-only proof of native or distributed behavior, no live provider spend required.
4. Read-only gates must not write fixtures directly. Add Q.* audited QA units first, and release contested leases while waiting on owner subunits. Any new/repaired artifact, schema, wiring or test inherits the same Go context, minimal-marked-diff, candidate/integrated audits and actual test gates. No "cleanup" PR bypasses checks. Exact scope/authority overrides cosmetic footprint count.
